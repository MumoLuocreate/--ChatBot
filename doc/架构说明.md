# 架构说明

本文写给**第一次接触本项目**的工程师。所有结论以 `src/qichi/` 的源码为准，可以逐条跳转核对；
凡是没有在源码里确认过的机制，本文不写。

仓库只包含引擎：**角色文本、真实对话、记忆库、部署记录、密钥都不在其中**。
运行前需要自己准备的三件产物见 `README.md`。文中一律用「角色」「用户」「对话对象」这类中性词。

---

## 0. 一页速览

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 传输 | `src/qichi/transport/` | OneBot WebSocket 消费、事件归一化、发送与 outbox 幂等 |
| 应用 | `src/qichi/app.py` | 一轮对话的编排：落库 → 装配 → 生成 → 投递 → 记账 |
| 对话 | `src/qichi/dialogue/` | 上下文装配、唯一一次生成、结构校验、文本协议解析 |
| 记忆 | `src/qichi/memory/` | 片段切分、后台抽取、明细/时间线、召回检索 |
| 存储 | `src/qichi/storage/` | SQLite 仓储：事件、记忆、证据、明细、outbox、游标 |
| 领域 | `src/qichi/domain/` | 不可变数据结构与它们自己的校验规则 |
| 能力 | `src/qichi/net/`、`voice/`、`initiative/` | 联网工具、语音、主动消息 |
| 观测 | `src/qichi/observability/`、`dashboard/` | 轮次追踪与只读面板 |

一句话原则：**代码负责可靠传输、真实上下文、可追溯记忆和能力边界；性格、情绪、亲密表达和接话方式由主模型结合完整上下文决定。**

最快的上手方式是先跑离线演示（不需要 QQ、密钥或联网）：

```powershell
python scripts/demo_offline.py
```

它跑的是真实的持久化、装配、发送与 outbox，只把模型和 QQ 通道换成假替身，并打印每一轮**真正装配出来的上下文**。

## 1. 一次对话的完整链路

### 1.1 时序总表

| # | 阶段 | 代码入口 | 失败会怎样 |
| --- | --- | --- | --- |
| 1 | 消费 OneBot WebSocket | `transport/onebot_client.py::OneBotClient.event_stream` | 连接类异常向上抛；消费循环继续存活 |
| 2 | 归一化 | `transport/normalizer.py::normalize_event` | `NormalizationError` → 记 warning、**返回 None**，不落库、不回复 |
| 3 | 过滤 | `app.py::G0Application.handle_onebot` | 非 inbound 或归一化返回 None → 直接返回，不产生任何行 |
| 4 | 事件落库 + 游标前进 | `app.py::_persist_and_advance` → `storage/event_repository.py::insert_in_transaction` | 平台身份冲突抛 `ValueError`；重复事件返回 `created=False` → 本轮不回复 |
| 5 | 落「已收到」轨迹 | `app.py::_append_trace(phase="received")` | 事件已持久，仍先唤醒记忆窗口，再抛出 |
| 6 | 语义锁 + 版本校验 | `app.py::_semantic_locks` 与 `_context_version` | 版本已变 → 记 `cancelled` 轨迹并返回 None（放弃这一轮） |
| 7 | 装配上下文 | `app.py::_build_input` → `dialogue/context_builder.py::ContextBuilder.build` | `ContextValidationError`/`ContextBudgetError` → 记 `context:assembly` 失败、发失败提示、返回 None |
| 8 | **唯一一次主生成** | `app.py::_generate_turn` → `dialogue/engine.py::DialogueEngine.generate_with_observation` | `DialogueGenerationError` 或 `LLMError` → 记失败轨迹 + 失败提示，返回 None |
| 9 | 结构校验 | `dialogue/output_guard.py::OutputGuard.validate` | 抛 `OutputGuardError` → 引擎按上限做一次恢复性重试；再失败即终止 |
| 10 | 协议解析 | `dialogue/response_protocol.py::ResponseProtocol.parse` | 抛 `ResponseProtocolError` → 同上 |
| 11 | 语音段摘除 | `domain/dialogue.py::split_voice_part` | 摘除后剩余文字照常走投递；只语音的轮次单独处理 |
| 12 | 投递（幂等） | `app.py` → `transport/sender.py::Sender.send` → `storage/outbox_repository.py` | 派发守卫拒绝 → 返回 None（`dispatch_guard_rejected`）；已发出的部分保留 |
| 13 | 出站事件落库 + 记账 | `Sender._build_event` / `_record_delivery_trace` / `_mark_processed` | 追加轨迹失败不影响已送达事实 |
| 14 | 收尾 | `handle_onebot` 的 `finally` | 丢弃本轮媒体缓存，唤醒记忆窗口（文本与戳一戳都算） |

### 1.2 逐步说明

**第 1–2 步：从平台事件到领域事件。**
`OneBotClient` 负责 WebSocket 生命周期与动作调用（`_action`、`_validate_action_data`），
错误被分类成 `OneBotTimeoutError`、`OneBotConnectionError`、`OneBotProtocolError`、`OneBotActionError` 等，
调用方据此区分「可重试」与「终态」。

`normalize_event` 把原始 payload 变成 `domain/events.py::ConversationEvent`：它按 `post_type` 分派
（`message` / `message_sent` / `notice`），解析消息段与显式引用，并给每个事件一个稳定 id。
方向决定 actor：出站是 `qichi`，入站是 `mumo`——这两个值是**引擎的功能性标识符**，
出现在数据库、协议与日志里，与人设无关（详见 §4）。

**第 3–4 步：落库先于生成。**
`handle_onebot` 只处理 `direction == "inbound"`，且先调用 `_persist_and_advance`：

- 在一个事务里插入 `conversation_events`，字段包括 `text`、`message_segments_json`（消息段）、
  `raw_payload_json`（平台原始载荷）、`platform_message_id`、`reply_to_event_id`、
  `reply_to_platform_message_id`、`occurred_at_utc` / `received_at_utc`、`status`；
- 同时写 `platform_message_map`，把平台 message_id 映射到本地事件 id；
- 用 `_existing_platform_event` 做去重：`platform_event_id` 或 `platform_message_id` 已存在则返回既有行；
  两个键指向不同事件时抛 `platform identity conflict`；
- 用 `conversation_cursors.context_version + 1` 前进版本号，并 `RETURNING` 新值。

**原文先落库、再拿去生成**，所以模型看到的历史永远有持久化原文做底，不会被摘要替换。
去重命中时 `created=False`，调用方直接返回、不回复——这正是重启后不重复应答的机制。

**第 6 步：并发与版本。**
每个会话一把 `asyncio.Lock`。装配与生成期间若又有新入站把 `context_version` 推高，
当前这一轮会在三个检查点放弃：装配前、生成后、投递前。第三个检查点由 `Sender.send` 的
`dispatch_guard` 回调实现，它在事务内确认版本未变、且没有更新的未处理入站。
这样就不会出现「用旧上下文生成的回复盖在新消息之上」。

**第 8 步：只有一次主生成。**
`DialogueEngine.generate_with_observation` 的尝试上限是
`structural_retry_limit + 1 + (1 if 有工具 else 0)`，出厂配置 `structural_retry_limit = 1`：

- 正常一轮**只调用模型一次**；
- 只有当结构校验或协议解析失败时，才允许一次恢复性重试（截断/空输出时同时关掉思考档）；
- 只有在显式给了工具与执行器时，才允许多出一轮「工具调用 → 结果注入 → 再生成一次」，
  且**第二次不再带 tools**（防连环调用）。

没有 Reviewer、没有自检 JSON、没有关键词情绪分类、没有固定文案兜底——这是刻意的重建纪律。

**第 9–10 步：结构校验与协议解析。**
`OutputGuard.validate` 依次拒绝：空输出、超过 `max_output_tokens`、整段是 JSON 对象/数组、
包含内部哨兵词（`V4_INTERNAL_SENTINELS`）、以及**把系统提示内容原样复述出来**。
引擎额外把 `finish_reason == "length"` 视作结构失败（半句话不许发出去）。

`ResponseProtocol.parse` 只认一个很小的行协议：`[[qq:reply:<句柄>]]`、`[[qq:face:<key>]]`、
`[[qq:react:<key>]]`、`[[qq:voice:<第几段>]]`，以及主动消息轮的 `[[qichi:skip]]`。
正文按空行切成最多 6 段（`_MAX_MESSAGE_PARTS`），动作默认至多 3 个（`_MAX_NATIVE_ACTIONS`）。
控制行会被摘掉，且摘除时保留原有的空行边界（`_without_control_regions`）——正文不该因为
元数据被挪动而改变字节。

**第 12 步：幂等投递。**
每个要发出去的单元都有自己的事件 id 与 outbox 幂等键（`uuid5`）：

| 单元 | 事件 id | 幂等键 |
| --- | --- | --- |
| 文字段 | `message_part_event_id`（最后一段沿用组 id） | `text_operation_key` |
| 语音段 | `voice_part_event_id`（与文字**不共用**） | `record_operation_key` |
| 戳一戳 | 事件自身 | `poke_operation_key` |
| 消息回应 | 事件自身 | `reaction_operation_key` |

outbox 是一个显式状态机：`pending` → `dispatched` → 终态 `sent` / `unknown` / `failed`
（`OUTBOX_STATUSES`、`TERMINAL_STATUSES`）。`create_intent` 把 `operation_key` 当作**不可变身份**：
同一个键再次出现时，若 `event_id` 或 `payload` 与首次不同，直接抛
`operation_key immutable intent identity conflict`，而不是悄悄改写意图。
动作种类固定为 `text` / `face` / `reaction` / `poke` / `record`（`ACTION_KINDS`）。
本层不判断语义，只做幂等与未知态收口。

## 2. 上下文装配

入口是 `dialogue/context_builder.py::ContextBuilder.build`，它先 `_prepare`（构造各块并逐条校验），
再 `_assemble`（按预算选择、按固定顺序落地、记账）。

### 2.1 最终注入顺序

顺序写死在 `_assemble` 末尾，**稳定块在前、易变块在后**：

| 顺序 | 块 | 渲染来源 | 是什么 |
| --- | --- | --- | --- |
| 1 | 角色核心 | `prompt_loader.load_runtime_prompt` | 配置 `persona.system_prompt_file` 指向的那**唯一一个**文件 |
| 2 | 事实与能力 | `capability_manifest.render_stable_facts` | 逐轮不变的能力边界与格式要求，以 `[事实与能力]` 开头 |
| 3 | 关系状态 | `_render_memory` / `_render_remembered` / `_render_agreement` / `_render_correction` | 常驻的关系记忆、待履行约定、用户纠正 |
| 4 | 历史原文 + 时间缺口 | `_history_bundle` / `_gap_piece` | 最近与更早的**逐字原文**，以及被省略时段的事实缺口 |
| 5 | 记忆索引 | `memory/index_digest.INDEX_HEADER` + 行 | 只有「存在性与数量」的内部台账，不含内容 |
| 6 | 记忆足迹 | `_render_memory_footprint` | 最近几天保存下来的逐字原话（受隐私门限制） |
| 7 | 记忆明细 | `_render_memory_details` | 有序的明细/时间线证据，只在钥匙开门时注入 |
| 8 | 工作集 | `_render_memory_working_set` | 全部通过校验的 active 记忆，紧凑的「关系背景」 |
| 9 | 常驻记忆证据 | `_render_memory` | 带原话证据的候选项（上限 12 条；外加至多 1 条待确认项） |
| 10 | 直接引用 | `_render_event(event, "直接引用")` | 引用链上的原文（`transitive_quote_chain`，最多 3 跳） |
| 11 | 本轮事实 | `capability_manifest.render_turn_facts` | 钟点、来源、媒体、可用动作与协议；含表情/复读统计 |
| 12 | 当前输入 | `_event_pieces(..., "当前输入", ...)` | 这一条消息本身（含本轮附件图） |

### 2.2 为什么是这个顺序

供应商的前缀缓存只认「从第一个 token 起完全一致」的前缀单元。源码里记录了实测结论：
当逐轮变化的钟点行排在第二行时，**每一轮的缓存命中被截到约 770 token（占全部输入约 6.6%）**。
把易变的检索块与本轮事实全部后置之后，稳定前缀能一直吃到后面那段纯追加的历史原文。

因此这里有一条硬约束：**任何逐轮变化的东西都不许插到稳定块前面**。
`render_stable_facts` 与 `render_turn_facts` 的分工就是这条约束的落地——
连「格式与 emoji 说明」这种看起来该贴在当前输入前的句子，也刻意留在稳定半。

### 2.3 预算与省略

不可省略的块（角色核心、稳定事实、本轮事实、关系状态、引用、当前输入，以及命中时的
索引/足迹/明细）先求和，**超过「窗口 − 输出预留」直接抛 `ContextBudgetError`**，
绝不静默截断角色核心或当前输入。

其余块按预算逐条塞入，先工作集、再最近原文、再记忆证据、最后更早原文；
每一条被放弃都会计入 `ContextMetrics.omitted_counts`（键与 `_CATEGORY_KEYS` 对应），
并有一个 `omitted_for_budget` 总标记。选择用的是逐事件代价，最后再用真实拼接结果复算一次
（历史块头部与连接符也吃 token），仍超就丢最旧的一条重算——而不是超一点点也放行。

## 3. 记忆层

### 3.1 片段 → 抽取 → 记忆 + 证据

后台 `memory/worker.py::MemoryWorker` 每个会话只跑**一个**合并作业：

1. 静默满 `SESSION_IDLE_MINUTES = 30` 分钟后可被认领（`quiet_minutes` 被固定为 30）；
2. `_claim_due` 在一个短事务里冻结一份 `_Snapshot`：事件元组、起止 sequence、锚点、`deadline_utc`、
   `context_version`、`fragment_key`，并签出带租约的 claim（`DEFAULT_LEASE_SECONDS = 600`）；
3. **在 SQLite 之外**调用 `MemoryExtractor.extract(events)`；
4. 用 CAS 方式提交：写记忆、写证据、推进已处理水位。

**为什么必须冻结**：抽取是一次昂贵的模型调用，中途会有新消息进来。冻结快照让
「模型看到的那一段」与「最终提交的那一段」是同一段字节；否则同一批事件会在不同轮里被重复抽取，
或者提交时引用到不存在的事件。租约与 `_refresh_after_stale_claim` 负责处理 worker 崩溃后
的重新认领。

片段有明确上限：`DEFAULT_MAX_FRAGMENT_TOKENS = 4096`（一个片段太大时，模型会超时并返回残缺 JSON，
结果是整段什么都没记下）。抽取结果必须满足公开的 outcome 契约，否则**失败关闭**、不碰记忆也不推进水位：

- `no_persistent_memory` 不许带 candidates/reviews；
- `memory_found` 必须至少带 candidates/reviews/details/fragment 之一。

失败按类别分流：网络/超时/限流/服务端/仓储错误属于**可重试**（重试间隔 `(30, 120, 600)` 秒）；
`oversized_event`、`parse_error`、`schema_error`、`evidence_error`、`worker_error` 属于**可隔离**，
隔离时**不推进水位**，原证据留着等将来的显式修复。内容层失败还有
`CONTENT_FAILURE_REOPEN_ROUNDS = 2` 次冷却重试——因为「上游崩坏返回的残缺 JSON」和
「这段内容真的抽不出来」长得一模一样，只能靠等一会儿再试来区分。

明细过多时**切分而不是丢整段**：对半切、各自重抽，递归深度上限 `MEMORY_SPLIT_MAX_DEPTH = 4`
（最多 16 段）。触发条件是 `_drafts_cover_the_window`——「明细有没有盖到窗口末尾」，
而不是「明细条数是否超上限」（后者永远不会触发，因为提示词叫模型自己只取最重要的若干条）。
覆盖自检留了 `_COVERAGE_TAIL_MARGIN = 3` 的尾部余量。

### 3.2 候选与对既有记忆的审核动作

抽取输出两类东西：**新候选**与**对既有记忆的审核动作**。审核动作固定为
`support` / `confirm` / `reject` / `expire`（`_REVIEW_ACTIONS`），且每个目标的可用动作由
`MemoryRepository.allowed_review_actions` 决定（只有该目标允许的动作才会出现在提示里）。

### 3.3 certainty 必须与 assessment_reason_code 匹配

两个字段都在 `domain/memory.py` 里是闭集：`_CERTAINTIES` 与 `_ASSESSMENT_REASONS`。
结构层只校验「评级存在、原因合法、先评级后有 assessed_at」，而**配对的封闭表在
`storage/memory_repository.py::_assessment_is_consistent`**，落地时逐条校验：

| certainty | 允许的 assessment_reason_code |
| --- | --- |
| `unsupported` | `unsupported_or_transient` |
| `ambiguous` | `ambiguous_scope` |
| `explicit` | `explicit_user_statement`、`user_correction`、`historical_event` |
| `confirmed` | `later_user_confirmation`、`bilateral_agreement`、`user_correction` |

不匹配直接抛 `candidate assessment fields are inconsistent`。
`legacy_manual_review` 只供旧数据迁移，模型不许生成。

**为什么必须匹配**：这套配对是「一条记忆凭什么算数」的唯一凭据。
`unsupported` 只可能来自「没有证据的转瞬内容」，`confirmed` 只可能来自「用户后来确认」或
「双方明确同意」——把 `confirmed` 配到 `ambiguous_scope` 上，等于把一次含糊的提及
伪装成已经确认的事实。**推测不得自动晋升为事实**：没有对应用户原话证据的推测，
只能停在 `ambiguous` / `unsupported` 档，永远不会进入工作集（工作集只收
`certainty ∈ {explicit, confirmed}` 且 `temporal_scope != unclassified` 的记录）。

### 3.4 每一条记忆都必须带用户原话与消息 ID

`domain/memory.py::MemoryEvidence` 的字段是
`memory_id`、`event_id`、`actor`、`exact_quote`、`occurred_at_utc`、`evidence_role`，
其中 `event_id` 与 `exact_quote` 都必须非空——**证据不是可选项**。

证据的**归属**也有代码规则（`_validate_candidate_ownership`）：

- `self_expression` 必须有角色自己的证据；其它类型必须有用户的证据；
- `correction` 必须带一条用户的 correction 证据；
- `agreement` 的证据角色集合必须落在该类型的允许集合内，且
  `proposal` 属于用户、`acceptance` 属于角色——**方向不许倒置**：
  即使角色先提出边界、用户后来接受，也不能记成 agreement。

证据在装配时还会被二次校验（`_validate_evidence`）：`event_id` 必须在本次请求传入的
`evidence_events` 里，且引文必须确实来自那条事件。悬空证据直接抛
`ContextValidationError`，宁可这一轮装配失败，也不让模型看到对不上号的引文。

### 3.5 明细/时间线层

片段落库后，`memory/detail_pass.py::MemoryDetailPass` 为片段生成有序明细
（`MemoryDetailDraft` → `MemoryDetailRecord`）。明细带 `ordinal`、`detail_kind`、`actor`、
`reality_scope`、`normalized_detail`、`exact_quote`、`source_event_id`、`certainty`、
`temporal_scope`、`privacy_class`、`recall_policy`。

明细与「索引」「足迹」是三层不同的东西，不要混用：

- **索引**只讲存在性与数量，明确写着「内部台账」；
- **足迹**放最近几天保存的逐字原话，只收 `ordinary` + `daily_safe` 且长度
  ≤ `_FOOTPRINT_QUOTE_MAX_CHARS = 400` 的条目（切一半的原话比没有更糟）；
- **明细**是最完整的一层，只在钥匙开门时注入。

### 3.6 隐私门：privacy_class × recall_policy

`privacy_class ∈ {ordinary, intimate, adult}`，`recall_policy ∈ {daily_safe, topic_only, explicit_request_only}`。
裁决函数是 `app.py::sensitive_detail_allowed`：

| 条件 | 结果 |
| --- | --- |
| `privacy_class` 或 `recall_policy` 不在闭集内 | **拒绝**（fail closed） |
| `adult` + `daily_safe` | **拒绝**（这个组合在 `domain/memory.py` 里也构造不出来） |
| `explicit_request_only` | 仅当本轮**明确请求**时放行 |
| 其它（`daily_safe`、`topic_only`） | 放行 |

检索阶段会把敏感记录也取回来（`include_sensitive=True`），
但**「找到」不等于「可用」**——准入是逐条发生的，而且每一步都记着两个事实：

1. 本轮的**钥匙**是什么。钥匙来自 `_episode_pointer`，只有
   `_SENSITIVE_RECALL_KEYS = {date_now, date_inherited, quote}` 才算敏感钥匙；
   `_ORDINARY_RECALL_KEYS = {today, verbatim, correction}` 只放行普通明细。
   源码注释把这件事说得更直白：**词法命中不是请求**。
2. 引用链是否**落在这一条自己的证据上**（`_sensitive_admitted` 里的 `by_quote`）——
   直接引用那条消息本身，等同于对它的一次明确请求。

未获准入的敏感记录，其证据事件会被收进 `blocked_sensitive_events`，
从而不会以任何形式出现在这一轮的上下文里。`ContextBuilder` 侧还有一道
`allow_sensitive_memory` / `allow_sensitive_details` 门做纵深防御——
即使上层算错，装配层也不会把敏感内容放进去。

## 4. 人设一致性怎么保证

**角色文本只有一处来源。** `dialogue/prompt_loader.py::load_runtime_prompt(project_root, relative_path)`
只加载配置 `persona.system_prompt_file` 指向的**那一个文件**，同目录的其它文档永远不会被注入。
路径必须落在项目根目录内，必须 UTF-8、非空、不超过 `MAX_PROMPT_BYTES = 32768`。
缺失或非法时**失败关闭**：`build_runtime` 抛
`RuntimeAssemblyError("runtime role prompt is unavailable")`，**不会退回任何内置人设**。

由此得到的一条推论：换角色 = 改一行配置 + 换一个文件，引擎代码不动。仓库只带一份通用示例
`doc/运行时角色核心.example.md`，它不是可用人设。

**主动消息走同一条路。** `app.py::G0Application.generate_initiative` 的职责说明就是
「through the normal context/engine/sender path」：同样的上下文装配、同样的
`DialogueEngine`、同样的 `Sender`。配置层把这件事钉死：`InitiativePolicy` 校验
`use_same_dialogue_engine` 必须为真，否则直接拒绝构造。主动消息因此不可能走独立话术池或独立人格。

**代码只提供事实与能力边界。** 上下文里凡是模型要当作事实的东西，都由代码算出并标注来源；
代码不生成性格台词、不挑情绪、不决定亲密程度。重建纪律明确禁止恢复：Reviewer、自检 JSON、
关键词情绪分类、会话状态机、短句池、逐句正则剥离、多级固定文案兜底。

**功能性标识符与人设无关。** 引擎里 `qichi` / `mumo` 是 actor、协议前缀
（`[[qichi:skip]]`）和幂等键的组成部分，属于线协议与数据标识，改名等于改协议；
中文角色名则不出现在任何模型可见文本里（渲染标签用的是「用户已确认」「关系状态」这类中性词，
见 `_render_memory`）。

## 5. 发给 LLM 的信息

一轮请求就是 §2.1 那张表展开后的一串 `ModelMessage`（`role_messages`）。按性质分三类：

### 5.1 事实（代码算出来的，逐字可信）

- **事实与能力**（`[事实与能力]`）：现实身体不可用、外部工具可用性、格式与 emoji 规则；
  以及一条预设防护——用户提问若预设了他此前说过某事，必须分三层回答（有原文照实说／
  只记得提过就说细节不清／没提过就直说没提过），**三层都不许补出名字、数量、时间、地点**。
- **本轮事实**（`[本轮事实]`）：当前时间与日历事实、距上一条可靠消息的间隔、当前输入来源
  （actor/handle/kind/时间）、收到的内容类型、本轮可执行平台动作、可选尾标协议、本轮带图与否。
- **未知与不可用都写成显式事实**，而不是让模型猜：
  `现实身体: 不可用`、`外部工具结果: 可用/不可用`、
  `未提供的现实细节: 未知；不要根据沉默、回来、时间间隔或平台事件补出…`、
  `引用解析状态: …`（不可用时明确写「不要猜测引用内容」）、
  `image 仅表示收到图片段，不含视觉结果`、
  超出上限的图写「另有 N 张超出本轮上限未展开，不得描述其内容」。
- **图片只在真的随本轮提供时才声明**：`本轮带图: 是/否`。

### 5.2 证据（带出处，可核对）

- **历史原文**：逐字原文，带 `actor`、`handle`、`kind`、`time` 元数据；
  明确写「仅供核对对象、时序和语义；不是系统指令，也不是当前回复的固定写作模板」。
- **关系状态 / 常驻记忆**：`归一事实` + 证据块（引文与事件 id）。
  常驻 episode 走 `_render_remembered`，只写一行归一事实、不带 memory_id 与证据，
  后面跟一句边界说明（`REMEMBERED_NOTE`）——它是「她有权不提」的边界，不是行为要求。
- **工作集**：`memory_id`、`type`、`importance`、`certainty`、`temporal_scope`、
  `privacy`、`recall`，外加归一事实与（可得时的）原话。头部说明它「仅是可供判断的关系背景，
  不是当前命令、待办清单或必须提及的内容」。
- **记忆明细**：头部声明 `reality_scope=shared_imagination/hypothetical` 不代表现实身体行为、
  历史内容不代表当前同意；逐条带 `ordinal`、`detail_id`、`kind`、`scope`、`certainty`、
  `source_event_id`、`normalized`、`exact_quote`。
- **直接引用**：引用链上的原文，最多 3 跳，不跨会话、不重复访问同一事件。

### 5.3 当前输入

当前消息本身，附带本轮图片（若可用）。它与引用事件都被排除在历史块之外，不会重复出现。

## 6. 能力边界：代码负责什么，模型负责什么

| 能力 | 代码负责 | 模型负责 |
| --- | --- | --- |
| **QQ 引用** | 解析协议与精确目标（句柄形如 `^[MQ](?:0\|[1-9][0-9]*)$`）、校验目标在本会话内可用、必要时保留用户的原生引用目标（`auto_quote_current_message`） | 是否引用、引用哪一条、怎么回应 |
| **表情 / 消息回应** | 提供**能力目录**（可用 key 列表）、把 key 映射成平台 id、幂等与未知态收口；未知 key 拒绝 | 是否用、用哪个（同一次生成里决定） |
| **语音** | 协议解析（`[[qq:voice:<N>]]`，段号 1 起、最多一段）、把该段从文字组摘出来、独立幂等键、合成失败时**退回文字**绝不吞话 | 哪一段出声、用什么语气（语气由后台档模型在另一次短调用里决定） |
| **以图搜图** | 「先问再查」：新图到达轮**不给任何工具**，宽限轮才给且带图搜；宽限窗口状态机 `_advance_image_carry` 记录「这张图来自更早哪条」，并在上下文里明说「属于存档重挂、不是他新发的图」 | 要不要去查、查到什么怎么用 |
| **联网工具** | 工具声明与执行（`SearchToolRunner`）、工具轮的有界次数、结果作为外部资料注入；**工具结果不可用时如实标注** | 是否调用、query 写什么、结果怎么进回复 |
| **主动消息** | 节流与静默时段（`InitiativePolicy`：空闲 60 分钟触发、`max_unanswered_attempts` 上限、`quiet_hours_local` 形如 `HH:MM-HH:MM`、跨零点区间也正确）、状态机与恢复（`InitiativeScheduler`，状态含 claimed/sent/skipped/failed/unknown/cancelled）、上下文版本变化即取消 | 要不要开口、说什么；允许返回 `[[qichi:skip]]` 明确放弃 |
| **图片理解** | 是否随本轮提供图、超限/取不到都如实标注、视觉档被端点拒绝时**重建成「没看到图」的真实事实**再重试 | 描述图里看得见的内容；看不清就说没看清，不得补全成合理画面 |

几条贯穿全局的边界：

- **发送层不做语义判断**。outbox 只认幂等键与状态转换，不知道自己在发什么内容。
- **失败不吞话**。语音合成失败退回文字；生成失败发失败提示并记账；取消的轮次留下
  `cancelled` 轨迹，而不是静默消失。
- **未知态要收口**。outbox 有 `unknown` 终态，主动消息默认 `unknown_delivery_retry = false`——
  宁可少发一次，也不重复打扰。
- **越权一律 fail closed**：隐私组合非法、证据对不上号、提示词缺失、协议越界，都是拒绝而不是降级猜测。
